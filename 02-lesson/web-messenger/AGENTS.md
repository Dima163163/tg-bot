# Инструкция для `web-messenger`

Эти правила действуют для файлов внутри `web-messenger/`. Выполняй также инструкции более высокого уровня и явные требования текущей задачи. Цель этой инструкции — развивать клиентское приложение по подходу page-first FSD и осознанно размещать состояние в React, Zustand, URL или TanStack React Query.

## Карта проекта

Клиент — SPA на React, строгом TypeScript и Vite. Маршруты настроены через TanStack React Router. Zustand уже установлен для клиентского состояния, TanStack React Query — для данных сервера. Перед изменением API или синтаксиса библиотек сверяй фактические версии в корневом `package.json`.

| Путь | Ответственность сейчас |
| --- | --- |
| `src/main.tsx` | Вход в React-приложение и `StrictMode`. |
| `src/app/App.tsx` | `QueryClientProvider` и `RouterProvider`; здесь создаётся конфигурация Query Client. |
| `src/app/router.tsx`, `src/app/app.css` | Дерево маршрутов, глобальные стили и подключение страниц. |
| `src/pages/messenger/MessengerPage.tsx` | Сборка экрана диалогов, запросы, состояния загрузки и взаимодействия. |
| `src/pages/articles/` | Страница `/articles`: список статей, курсорная подгрузка и действия создания, редактирования и удаления. |
| `src/pages/messenger/model/store.ts` | Состояние интерфейса мессенджера в Zustand. |
| `src/pages/messenger/model/client.ts`, `message.ts` и `use-realtime-messages.ts` | Типы, запросы и Realtime-подписка страницы; текущий проект пока держит их в `model/`. |
| `src/pages/articles/model/article.ts`, `use-articles.ts` | Тип статьи, проверка ответов Edge Function, CRUD-запросы и React Query hooks для курсорных страниц и мутаций. |
| `src/shared/api/edge-functions.ts`, `supabase-config.ts` и `realtime-client.ts` | Общий HTTP-транспорт, конфигурация Supabase и singleton-клиент Realtime. |
| `src/shared/ui/`, `src/shared/lib/` | Общие UI-примитивы и технические утилиты. |

Команды запускаются из корня репозитория: `npm run dev` поднимает Vite, `npm run build` выполняет TypeScript-сборку и Vite build. `npm test` сейчас проверяет webhook в `supabase/` и не является проверкой клиентского интерфейса. В `tsconfig.app.json` включён `strict`; алиасы импортов в текущей конфигурации не настроены.

## Page-first как рабочий подход

Page-first означает порядок разработки: сначала реализуй законченный пользовательский сценарий внутри слайса страницы, затем выделяй повторно используемые или самостоятельно принадлежащие части в нижние слои FSD. Это проектное соглашение о развитии кода, а не новый слой FSD.

1. Найди маршрут, точку входа страницы, данные, действия пользователя и состояния интерфейса. Определи, что должно работать в итоге.
2. Начинай реализацию в `src/pages/<page>/`. Код, нужный только этой странице, остаётся там: разметка, локальные компоненты, модель, запросы и стили.
3. По мере роста добавляй сегменты `ui/`, `model/`, `api/`, `lib/`. Создавай только те каталоги, где уже есть код с понятной ответственностью. Не заводи пустые слои и файлы для соблюдения шаблона.
4. Сначала добейся цельного сценария с загрузкой, ошибкой, пустым состоянием и основным действием. После этого оцени, какие части действительно следует извлечь.
5. Не проводи широкую реорганизацию соседних страниц ради одной локальной задачи. Если изменение выявило архитектурный долг вне задачи, укажи его отдельно.

У страницы нет искусственного ограничения на объём: большой блок, используемый только здесь, может оставаться внутри страницы. При этом разделяй файлы, когда это облегчает навигацию и разграничивает отображение, состояние и доступ к данным.

### Как выбрать слой

| Слой | Помещай сюда | Не помещай сюда |
| --- | --- | --- |
| `app/` | Запуск, маршрутизатор, провайдеры, глобальную конфигурацию. | Логику одного диалога или одной страницы. |
| `pages/<page>/` | Сборку экрана и код, принадлежащий маршруту. | Общую для нескольких экранов предметную модель после появления реального повторного использования. |
| `widgets/<name>/` | Крупный самостоятельный блок интерфейса, который повторяется или образует независимую часть сложной страницы. | Каждый небольшой компонент страницы. |
| `features/<action>/` | Значимое действие пользователя с собственной логикой, особенно если оно используется в разных местах. | Любой обработчик клика только потому, что это действие. |
| `entities/<name>/` | Общий предметный объект, его типы, модель, представление или относящийся к нему API. | Каждый DTO, существующий только для одного экрана. |
| `shared/` | UI-примитивы, общий транспорт API, технические библиотеки и конфигурацию без предметной привязки. | Специфичную для мессенджера бизнес-логику. |

Не добавляй слой `processes/`: в актуальном FSD он помечен как устаревший. Если многошаговый сценарий проходит через несколько страниц, выбирай владельца среди `features/` и `app/` по его ответственности.

### Зависимости и публичные API

Порядок слоёв сверху вниз: `app → pages → widgets → features → entities → shared`. Слайс может импортировать другой слайс только из слоя ниже; промежуточные слои можно пропускать. Файлы внутри одного слайса могут импортировать друг друга.

- `pages/a` не импортирует `pages/b`; `features/a` не импортирует `features/b`. Даже публичный API соседнего слайса не отменяет базовое правило зависимостей. Общую часть переноси в подходящий нижний слой или собирай взаимодействие на уровне выше.
- `entities` по умолчанию также изолированы друг от друга. Для необходимой связи двух сущностей используй явный интерфейс `@x` по правилам FSD и объясни, почему связь нужна.
- `app` и `shared` не разбиваются на предметные слайсы как остальные слои; их сегменты могут взаимодействовать внутри своего слоя.
- Когда слайс нужен снаружи, создай узкий публичный вход, обычно `index.ts` в корне слайса. Экспортируй только предназначенные для внешнего использования компоненты, типы и функции. Снаружи импортируй через этот вход, а не из `model/internal-file` или `ui/internal-file`.
- Внутри слайса используй прямые относительные импорты. Не создавай цепочки `export *` и `index.ts` для локального кода без внешних потребителей.
- Текущий `app/router.tsx` импортирует `MessengerPage.tsx` напрямую. Это существующее соглашение; не перестраивай его отдельно от задачи. Для новой страницы можно сразу дать её слайсу `index.ts` и импортировать страницу через него.
- Используй действующие относительные пути. Не вводи алиасы только ради формы FSD; если алиасы действительно нужны, согласуй изменения Vite и TypeScript вместе.

Пример постепенного роста новой страницы:

```text
src/
  app/
    router.tsx
  pages/
    reports/
      ReportsPage.tsx
      index.ts                 # если страницу импортируют снаружи
      ui/                      # только при появлении локальных компонентов
      model/                   # только при появлении модели или store
      api/                     # только при появлении запросов страницы
      reports.css
  shared/
    api/
    ui/
```

`widgets/`, `features/` и `entities/` добавляются позже при появлении их ответственности. Не создавай все показанные сегменты заранее.

## Куда помещать состояние

Перед созданием store или нового поля ответь, кто владеет состоянием и должен ли оно пережить смену страницы.

| Данные | Владелец | Пример |
| --- | --- | --- |
| Состояние одного компонента или нескольких близких дочерних компонентов | React `useState` или `useReducer` в ближайшем общем владельце, передача через props. | Открыта ли локальная панель. |
| DOM-узел или временная величина без необходимости рендера | `useRef`. | Ссылка на область прокрутки, высота перед подгрузкой. |
| Состояние, которое должно быть в ссылке, истории браузера или закладке | Параметры маршрута или поиска TanStack Router. | Выбранный диалог, если появится требование открыть его прямой ссылкой. |
| Совместное клиентское состояние удалённых друг от друга компонентов | Узкий Zustand-store владельца, когда подъём состояния и props делают поток данных неудобным. | Текущий выбор или счётчик новых сообщений на экране. |
| Данные и статус запроса к серверу | TanStack React Query. | Список клиентов, страницы истории сообщений, загрузка и ошибка. |
| Значение, вычисляемое из перечисленного | Вычисление при чтении, при необходимости `useMemo`. | Отфильтрованные клиенты, выбранный клиент, отсортированная история. |

Не создавай две независимые истины для одних данных. Если состояние переезжает в URL, не поддерживай отдельную конкурирующую копию в Zustand. Не копируй ответ Query в store только для доступа из других компонентов: они могут читать тот же ключ запроса.

## Правила Zustand

Используй Zustand для клиентского состояния с ясным владельцем. Существующий `useMessengerStore` — образец размещения store рядом со страницей; его поля `selectedClientId`, `search` и `newMessagesCount` относятся к поведению интерфейса, а не к серверному кэшу.

- Начинай store в `src/pages/<page>/model/`, если им пользуется только страница. При расширении области использования переноси состояние в слайс, который действительно им владеет; `app` подходит лишь для состояния всего приложения. Не собирай все страницы в один общий store.
- Явно типизируй данные и действия. Для нового TypeScript-store используй документированный синтаксис `create<Store>()((set) => ({ ... }))`; действующий `create<Store>((set) => ...)` не переписывай без причины.
- Давай действиям имена по намерению (`selectClient`, `clearNewMessages`), а не предоставляй компонентам произвольную запись в поля. Когда новое значение зависит от прежнего, используй функциональный `set((state) => ...)`.
- Zustand поверхностно объединяет обновления. Не изменяй вложенные объекты и массивы на месте; создавай новые значения или используй уже принятую в проекте стратегию иммутабельного обновления.
- Подписывай компонент на конкретные поля: `useMessengerStore((state) => state.selectedClientId)`. Не читай весь store ради одного значения. Объектные селекторы должны возвращать стабильный результат или использовать подходящее сравнение.
- Не храни значения, которые легко получить из Query и существующих полей store. Избегай эффектов, синхронизирующих две копии одного состояния.
- Store, созданный на уровне модуля, не исчезает при размонтировании страницы. Если сценарий требует сброса при выходе, спроектируй явное действие сброса и момент его вызова. Для нескольких независимых экземпляров одного экрана рассмотри фабрику store и локальный provider.
- Асинхронные запросы к серверу оставляй в React Query. Асинхронное действие в Zustand допустимо, если оно действительно управляет клиентским процессом и не дублирует загрузку, кэш или ошибки Query.
- Добавляй `persist`, middleware и devtools только по потребности задачи. При хранении в браузере выбери минимальный набор полей, предусмотри версию и миграцию формата и проверь восстановленные данные. Не сохраняй секреты.

Пример узких подписок; действие с функциональным `set` для счётчика уже есть в `pages/messenger/model/store.ts`:

```ts
const selectedClientId = useMessengerStore((state) => state.selectedClientId);
const selectClient = useMessengerStore((state) => state.selectClient);
```

## TanStack React Query и API

`QueryClientProvider` уже установлен в `src/app/App.tsx`. Используй этот клиент для серверных данных; не создавай второй клиент для страницы и не реализуй параллельный кэш в Zustand или `useEffect`.

- Для чтения используй `useQuery`; для курсорной истории — `useInfiniteQuery`. При изменении данных через интерфейс используй `useMutation` и адресную инвалидацию или точечное обновление кэша, если ответ мутации содержит полное новое значение.
- Ключ запроса — массив, описывающий ресурс и все параметры, от которых зависит результат. Для сообщений выбранного клиента ключ должен включать `clientId`. Курсор страницы у `useInfiniteQuery` передаётся как `pageParam`, а не подменяет идентичность списка в ключе.
- Не запускай запрос без обязательного ID: применяй `enabled` и обеспечивай корректную обработку отсутствующего ID в функции запроса и типах.
- Используй `isPending`, `isError`, `isFetching` и `isFetchingNextPage` по назначению; показывай загрузку, ошибку, пустой результат и подгрузку старых страниц без лишних локальных флагов.
- После успешного изменения инвалидируй подходящие ключи, а не весь кэш без причины. Не прячь ошибку запроса за пустым массивом, если для пользователя это разные состояния.
- Общий HTTP-механизм остаётся в `src/shared/api/edge-functions.ts`. Функции запросов и типы, относящиеся к одной странице, держи рядом с ней. Переноси их в `entities` или `features`, когда ими реально пользуются разные владельцы.
- Дженерик `callEdgeFunction<T>` задаёт тип компилятору, но не проверяет JSON во время выполнения. Для недоверенного или меняющегося ответа принимай `unknown` и проверяй структуру на границе API. Сохраняй существующие контракты ответа и обработку ошибок.
- Не размещай предметные функции вроде `getMessages` в `shared/api` только потому, что они вызывают HTTP. В `shared` должен оставаться общий транспорт и инфраструктура.

В текущем мессенджере ключ клиентов — `['clients']`, а ключ истории дополняется выбранным `clientId`. Обновление инвалидирует префиксы этих ключей. История загружается страницами через `nextCursor`; не переноси список страниц в Zustand.

## При изменении экрана мессенджера

Перед рефакторингом `MessengerPage.tsx` проследи весь поток данных и поведения:

1. `getClients` получает список клиентов; `getMessages` запрашивает страницы истории по `client_id` и курсору. Размер страницы задан константой `MESSAGE_PAGE_SIZE` в `model/message.ts` и сейчас равен 7. Типы и нормализация сейчас лежат в `pages/messenger/model/`.
2. Zustand хранит выбранного клиента, строку поиска и счётчик новых сообщений. Фильтрация клиентов и выбор объекта клиента вычисляются из данных Query и значений store.
3. Запросы автоматически обновляются каждые 30 секунд (`refetchInterval: 30_000`), а кнопка «Обновить» инвалидирует соответствующие ключи. Смена клиента меняет ключ истории.
4. Для подгрузки старых сообщений и сохранения позиции прокрутки используются `useRef` и обработчики скролла. Эти временные DOM-значения не относятся к Zustand.
5. Экран различает загрузку, ошибку и пустой результат для клиентов и сообщений. При разделении компонента сохрани эти состояния, доступность кнопок и поведение прокрутки.
6. `messenger.css` относится к странице; общие кнопки, поля ввода, аватары и остальные примитивы уже доступны в `shared/ui`.

Этот список описывает существующее поведение, которое нужно учитывать при затрагивающих его задачах. Он не требует немедленно разбить текущую страницу на `widgets` и `features`.

## TypeScript, UI и работа с файлами

- Соблюдай `strict` TypeScript: явно учитывай `null` и `undefined`, используй `import type` для типов, не обходи ошибки через `any` или необоснованные утверждения типов.
- Внешние DTO и значения после `JSON.parse` могут быть недостоверны независимо от TypeScript-интерфейса. Проверяй действительно важные поля перед использованием.
- Сохраняй существующие имена компонентов, стиль импортов и соглашения CSS. Новый общий UI-примитив помещай в `shared/ui` только если у него нет предметной привязки и есть обоснованный потребитель.
- Для пользовательского сценария учитывай семантическую разметку, клавиатуру, подписи элементов, состояния загрузки/ошибки/пустоты и узкие экраны. Не удаляй существующие `aria-*` атрибуты при разбиении компонентов.
- Не оптимизируй каждый рендер заранее. Узкие Zustand-селекторы и корректные ключи Query важнее механического добавления `useMemo` или `React.memo`. Мемоизируй вычисления, когда это упрощает данные или устраняет заметную работу.

## Порядок работы для нового изменения

1. Прочитай запрос, соответствующий маршрут, страницу, связанные `model`/`api`, общие примитивы и конфигурацию. Уточняй только те решения, которые нельзя разумно вывести из существующего кода.
2. Опиши для себя путь пользователя и источники данных. Разнеси каждое новое поле по таблице владельцев состояния выше.
3. Реализуй страницу в её слайсе. Добавляй локальные файлы только по появлению ответственности; сохраняй видимые состояния и доступность.
4. После работающего сценария проверь, возникли ли самостоятельный `widget`, повторяемая `feature` или общая `entity`. При извлечении сохрани публичный контракт и направление импортов.
5. Проверь, что нет дублирования серверного и клиентского состояния, запросы используют правильные ключи, а выбор/фильтрация не остаются в двух источниках истины.
6. Проверь типы, API-контракты и все затронутые пользовательские состояния. Для изменений TS/TSX используй `npm run build` из корня репозитория, когда нужна проверка сборки. При изменении взаимодействий проведи адресную проверку сценария; `npm test` покрывает webhook, поэтому не считай его подтверждением поведения UI.
7. В итоговом ответе кратко укажи, что изменено, почему выбран такой владелец кода или состояния и что действительно проверено.
