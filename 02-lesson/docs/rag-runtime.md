# Рабочий RAG: Groq + Supabase embeddings

Состояние проверено 2026-11-09 в проекте `cappgvetnxvjhnxufhkz`.
Миграции `20261109104038` и `20261109122047` применены. Функции
`articles`, `knowledge-admin` и `webhook` опубликованы. Telegram webhook
зарегистрирован на `/functions/v1/webhook/telegram` этого проекта.
Повторно настраивать текущий проект не требуется.

## Как получается ответ

1. Webhook проверяет секрет Telegram и вызывает `handleTelegramUpdateUseCase.execute`.
2. Репозиторий сохраняет входящее сообщение и получает lease ответа по update_id.
3. `answerKnowledgeQuestionUseCase.execute` проверяет вопрос длиной до 2000 символов.
4. Groq готовит краткое английское представление вопроса. Native Supabase
   `gte-small` вычисляет нормализованный вектор из **ровно 384 чисел**.
5. Репозиторий вызывает `search_articles` с той же моделью, top-3 и порогом 0.5.
6. Groq получает вопрос и оригинальные русские статьи. Если ответа в них нет,
   возвращает пустой список использованных источников. Приложение проверяет ID.
7. При наличии информации отправляется ответ с заголовками использованных статей.
   Иначе отправляется точный текст **«Мы обрабатываем ваш запрос»**.
8. После подтверждения Telegram ответ и состояние sent сохраняются одной транзакцией.

Пустой результат поиска сразу даёт fallback без вызова модели ответа.
Ошибка AI даёт сообщение о временной недоступности, а не выдуманный факт.
`/start` и `/help` показывают подсказку; вложение без подписи вызывает просьбу
написать вопрос текстом. Памяти диалога пока нет: вопрос должен быть самостоятельным.

## Зачем две модели

**Groq `openai/gpt-oss-20b`** понимает русский вопрос, готовит английский текст
для поиска и формирует ответ по найденным статьям. Название `openai/…` —
идентификатор модели, обслуживаемой Groq; запросы идут в `api.groq.com`.
Ключ OpenAI не нужен.

**Supabase `gte-small`** превращает текст в вектор для поиска по смыслу.
Она выдаёт ровно 384 измерения; 384 не означает длину статьи или максимум
количества символов. Встроенная модель рассчитана на английский и ограничена
512 токенами, поэтому перед ней используется английская проекция Groq до
480 ASCII-символов. Статья в БД сохраняется полностью на русском.

`intfloat/multilingual-e5-small` не используется: для выбранного пути без
отдельного модельного сервера взята встроенная модель Supabase.
На один обычный вопрос приходится один вызов Groq для проекции и, при наличии
кандидатов, второй для ответа. Сохранение статьи также требует вызова Groq.
При нарушении формата проекции допускается одна дополнительная попытка.

Model tag: `supabase/gte-small:groq-en-v1:openai/gpt-oss-20b`.
Смена модели проекции, embeddings или существенное изменение подготовки текста
требует нового tag и переиндексации статей. Одной одинаковой размерности мало.

## Статьи и архитектура

Одна строка articles — одна небольшая статья по одной теме. Новые title/body
проверяются, затем рассчитывается вектор, затем все четыре поля записываются
одним INSERT/UPDATE. UPDATE учитывает исходный updated_at. Ошибка провайдера
или конфликт не меняет старые текст и вектор. Триггера очистки embedding нет.

```text
Edge/HTTP или MCP stdin
  → именованный use case.execute(данные)
    → repository: PostgREST, SQL, условная запись
    → adapter: Groq HTTP, native Supabase AI, Telegram API
```

Прямые импорты, без DI. Общий RAG находится в
`supabase/functions/_shared/knowledge/`. HTTP/MCP не дублируют прикладные правила.

В БД созданы шесть демостатей о **вымышленном** коворкинге «Атлас»:
график, стоимость места, переговорная, интернет/печать, адрес/парковка, отмена.
У всех embedding(384) и одинаковый model tag. Старая запись «Проверка CRUD»
оставлена без вектора и в поиске не участвует.

## Настройки и публикация

В Supabase Secrets нужны:

| Имя | Назначение |
| --- | --- |
| `BOT_TOKEN` | Telegram Bot API. |
| `TELEGRAM_WEBHOOK_SECRET` | Авторизация входящего webhook. |
| `GROQ_API_KEY` | Ключ существующего аккаунта Groq. |
| `GROQ_MODEL` | `openai/gpt-oss-20b`. |
| `EMBEDDINGS_PROVIDER` | `supabase-groq`. |
| `RAG_ADMIN_TOKEN` | Случайный серверный секрет защищённого admin endpoint. |
| `RAG_MIN_SIMILARITY` | Необязательно; по умолчанию 0.5, не вероятность ответа. |

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` предоставляет Edge runtime.
Секреты не должны иметь префикс VITE_. В локальном .env для MCP нужны
EMBEDDINGS_PROVIDER, GROQ_MODEL, RAG_ADMIN_URL и RAG_ADMIN_TOKEN; Groq key локальному
MCP-адаптеру не нужен, он вызывает защищённый Edge endpoint.

Владельцу новой копии проекта нужно сначала настроить свой project_ref и URL,
затем выполнить из `02-lesson/`:

```sh
npm run db:push:dry
npm run db:push
npx supabase functions deploy articles knowledge-admin webhook --use-api
```

Dry-run показывает список без изменений. Push применяет миграции к связанному
удалённому проекту, сохраняя существующие строки. Deploy публикует только эти
три функции с их локальными импортами, без Docker и полного Supabase-стека.

Секреты можно задать в Dashboard → Edge Functions → Secrets. Для текущего project_ref
также есть `scripts/configure-knowledge.mjs`: он читает GROQ_API_KEY/GROQ_MODEL из
.env (либо явно указанного `--source-env path`), создаёт случайный admin token,
передаёт значения CLI через временный файл с правами 600, удаляет файл и настраивает
локальный MCP. Скрипт не печатает значения ключей. Не запускайте его для другой
копии без изменения project_ref и URL в самом скрипте.

## Защищённые служебные операции

`knowledge-admin` использует собственный Bearer RAG_ADMIN_TOKEN, а не JWT оператора.
`verify_jwt=false` нужен этому протоколу; без правильного секрета возвращается 401.
Endpoint не предназначен для браузера и не вызывает Telegram sendMessage.

Локальная presentation-утилита читает JSON из stdin:

```sh
node --env-file=.env scripts/knowledge-admin.mjs <<'JSON'
{"action":"seed"}
JSON
```

Seed создаёт отсутствующие демостатьи и индексирует записи с другим model tag;
существующие тексты не перезаписывает. При частичном сбое можно повторить.
Запускать одну seed-операцию одновременно: уникальность заголовка не задана в БД.
Для первоначального заполнения одной старой статьи:

```sh
node --env-file=.env scripts/knowledge-admin.mjs <<'JSON'
{"action":"index","id":123}
JSON
```

ID брать из действительного чтения articles. Action index пересчитывает вектор
и условно сохраняет текущие title/body/model по прочитанному updated_at.
Также поддержаны action embedding с text и action answer с question.
CLI для embedding печатает только размерность и model tag; локальный MCP-адаптер
получает сам вектор через HTTPS. Запись через MCP описана в [articles-setup.md](articles-setup.md).

## Ограничения и следующий этап

Пилот синхронно ждёт AI внутри webhook. Следующий блок — durable очередь:
сохранять задачу и быстро подтверждать Telegram, выполнять RAG в worker,
добавить ограниченные повторы и наблюдение за зависшими задачами. Двухминутный
lease уже защищает обычные повторы, но не гарантирует exactly-once отправку:
Telegram мог принять сообщение, а подтверждение или запись в БД — потеряться.
Автоматического фонового восстановления lease без следующего запроса пока нет.

Затем заменить демостатьи реальными небольшими материалами и расширить набор
вопросов для настройки top-K/порога. Английское сжатие может терять детали длинных
статей; текущие восемь вопросов не доказывают качество на любом русском корпусе.
Нагрузочное сравнение HNSW с точным поиском, per-user rate limits, метрики стоимости
и действие переиндексации в UI пока не реализованы.
