# План реализации RAG для Telegram-бота

- Дата: 2026-11-09.
- Статус: рабочий пилот опубликован в cappgvetnxvjhnxufhkz. Обе миграции применены; CRUD, embeddings, поиск и Telegram RAG подключены. Шесть демостатей проиндексированы. Шесть вопросов по статьям и два без ответа проверены через реальный API.
- Хранилище знаний: одна таблица `public.articles`; одна небольшая статья — один готовый чанк. Размерность embeddings — 384.
- Цель: Telegram-бот находит подходящие небольшие статьи и формирует ответ с опорой на найденные источники.

## Текущее состояние

Одна articles-запись является готовым чанком. CRUD сохраняет новый текст
вместе с пересчитанным вектором. Groq openai/gpt-oss-20b готовит английское
представление текста, native Supabase gte-small выдаёт embedding(384),
Groq отвечает по найденным оригинальным русским статьям. Это Groq API.

Webhook сохраняет входящее сообщение, получает двухминутный lease на ответ,
вызывает RAG и отправляет результат. Если подходящей информации нет,
возвращается «Мы обрабатываем ваш запрос». Успешная отправка записывается
вместе с состоянием sent одной транзакцией. Обычные повторы пропускаются;
конкурентная попытка получает retryable HTTP 502. Очередь пока не введена.

Пункты 1–6 ниже описывают уже реализованный основной сценарий и дальнейшее
развитие проверок. Пункт 7 отдельно разделяет действующий lease и будущую очередь.
Актуальные команды и ограничения — [rag-runtime.md](rag-runtime.md).

## 1. Новая миграция: одна таблица articles, vector(384), HNSW и поиск

Подготовлена [миграция add_article_embeddings_384](../supabase/migrations/20261109104038_add_article_embeddings_384.sql).
Файл создан Supabase CLI. Он расширяет существующую articles и сохраняет её
строки, идентификаторы, title/body, timestamps и контракт текущего CRUD.
Отдельная таблица фрагментов и автоматическое разбиение документов не нужны:
оператор изначально создаёт небольшие самостоятельные статьи.

### Состав миграции

1. Подключить vector в схеме extensions. Если расширение ранее установлено в
   другой схеме, завершить миграцию ошибкой без переноса чужих объектов.
2. Добавить embedding типа extensions.vector(384) и embedding_model типа text.
   Оба поля nullable: существующие статьи и новые записи из текущей панели
   остаются валидными до генерации embeddings.
3. Ограничением CHECK требовать заполнение embedding и embedding_model вместе;
   идентификатор модели должен быть непустым и без пробелов по краям.
4. Запретить нулевые векторы: для них cosine distance не определён.
5. Создать articles_embedding_hnsw_idx с vector_cosine_ops.
6. Сохранение согласованности текста и вектора поручить внешнему обработчику:
   сначала вычислить embedding нового текста, затем записать title, body,
   embedding и embedding_model одним UPDATE. Триггера очистки вектора нет.
7. Создать search_articles с SECURITY INVOKER и безопасным search_path.
8. Сохранить RLS и серверный доступ к articles; явно закрыть RPC для PUBLIC,
   anon и authenticated, разрешить выполнение service_role.

### Контракт поиска

```text
search_articles(
  query_embedding,        -- ровно 384 числа, ненулевой вектор
  query_embedding_model,  -- та же модель/конфигурация, что у статей
  match_count = 5,        -- допустимо от 1 до 20
  min_similarity = -1    -- диапазон [-1, 1]; по умолчанию без порога релевантности
)
→ id, title, body, similarity
```

Функция проверяет размерность явно: модификатор vector(384) нельзя использовать
как единственную проверку аргумента PostgreSQL-функции. Ищет только статьи с
ненулевым заполненным embedding и указанной embedding_model. Ранжирование —
по cosine distance `<=>` по возрастанию; similarity = 1 - distance.

Similarity не является вероятностью правильности ответа. Порог релевантности
подбирается на реальных вопросах. HNSW выполняет приближённый поиск; фильтр
модели и порог могут уменьшить количество результатов относительно match_count.
План запроса и качество индекса проверить после появления реальных данных.

### Проверка и применение

Подготовлен [SQL-сценарий проверки](../supabase/tests/article-embeddings-test.sql):
размерность, нулевые векторы, метаданные модели, поиск, фильтрация, аргументы RPC,
одновременное обновление текста и вектора, откат некорректного UPDATE,
удаление и ограничения доступа. Тестовые строки
откатываются через ROLLBACK; значения identity-последовательности могут увеличиться.

Полный локальный Supabase-стек не запускался. Повторная проверка удалённого
проекта 2026-11-09 подтвердила миграцию в истории, обе колонки и успешное
выполнение search_articles для синтетического запроса без совпадающей модели.
Триггера очистки embedding нет. Полный проверочный SQL выполнен на связанном
управляемом проекте: проверки прошли, тестовые строки откатились. Для повторения:

```sh
psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/article-embeddings-test.sql
```

Миграция не вычисляет embeddings и не меняет Telegram-ответ. Готовность статьи
к поиску на этом этапе определяется заполненным embedding; отдельные статусы
индексации, версии документов, таблица чанков и очереди не создаются.

Выбрана связка native gte-small(384) + Groq English projection для статей
и вопросов. E5 потребовал бы отдельного хостинга и в этом пилоте не используется.
Смена embedding-модели, Groq-модели проекции или версии подготовки текста требует
обновления model tag и переиндексации; совпадение размерностей недостаточно.

## 2. Единый адаптер embeddings

Реализован `_shared/knowledge/adapters/embeddings.ts`; серверный адаптер «текст → embedding», общий для индексатора и вопросов.
Проверять формат ответа, размерность и конечность числовых значений.
Предусмотреть таймауты, пакетную обработку, ограниченные повторы временных
ошибок и обработку лимитов провайдера.

Ключ Groq хранится в Supabase Secrets. Native gte-small работает на английском,
поэтому Groq создаёт ASCII-представление длиной до 480 символов, помещающееся
в лимит 512 токенов. Нестандартная пунктуация нормализуется; при нарушении
формата одна повторная попытка. Локальный MCP использует защищённую Edge Function,
а не пытается запускать native inference в Node.js.

Результат этапа: одинаковый проверяемый контракт embeddings для обоих потоков.

## 3. Пересчёт embedding перед сохранением статьи

Реализовать внешний серверный обработчик создания и изменения статьи:

1. Получить и проверить новый title/body. Для изменения прочитать текущую
   статью и сохранить её updated_at для контроля конкурентного редактирования.
2. Подготовить единый текст из нового title и body; автоматическое разбиение отсутствует.
3. Проверить ограничения приложения (title до 200, body до 12000 символов).
   Groq готовит короткое английское представление для поиска; исходная статья
   не обрезается при сохранении. Для точности поиска статьи должны быть небольшими
   и посвящёнными одной теме: длинная сводка может потерять детали.
4. Вызвать embedding-провайдера и проверить вектор из 384 чисел.
5. Для создания выполнить один INSERT с title, body, embedding, embedding_model.
   Для изменения выполнить один UPDATE с этими четырьмя значениями.
6. При изменении условие UPDATE должно учитывать исходный updated_at.
   Если статья удалена или уже изменена другим запросом, вернуть конфликт;
   устаревший запрос не должен перезаписать более новое редактирование.

Вызов провайдера выполнять до записи в БД. Если пересчёт завершился ошибкой,
изменения статьи не сохраняются: ранее сохранённые текст и вектор остаются
согласованными. Валидация vector(384) и CHECK-ограничения также должны откатывать
весь некорректный UPDATE, включая изменение текста.

База не проверяет смысловое соответствие embedding тексту. Каждый внешний
писатель обязан передавать согласованные title/body/embedding/embedding_model.
Этот сценарий подготовлен в application/use-cases/create-article.ts и
update-article.ts; общий prepareArticleContentUseCase.execute импортирует
адаптер напрямую. PostgreSQL-запись — в репозитории. Активен supabase-groq.
Если провайдер явно отключён, разрешена запись без векторов только для
неиндексированных статей; изменение индексированной отклоняется. Подготовленный CRUD поддерживает
редактирование title/body с expected_updated_at и выдаёт 409 при конфликте.
Порядок запуска и MCP — в [руководстве](articles-setup.md).

Результат этапа: новый текст и пересчитанный embedding сохраняются атомарно
и сразу доступны поиску после успешного сохранения.

## 4. Первоначальное заполнение embeddings

Подготовить внешний обработчик для существующих статей с embedding IS NULL.
Реализован indexArticleUseCase и защищённое action=index в knowledge-admin.
Он читает title/body/updated_at, вычисляет вектор и условно записывает embedding
и embedding_model, если строка не изменилась с момента чтения.

| Событие | Действие |
| --- | --- |
| Создание статьи | Рассчитать embedding, сохранить всё одним INSERT. |
| Изменение title/body | Рассчитать новый embedding, сохранить текст и вектор одним UPDATE. |
| Сохранение того же содержимого | При той же модели можно использовать существующий embedding. |
| Удаление статьи | Удаляется строка вместе с её embedding. |
| Ошибка провайдера при редактировании | Вернуть ошибку; сохранить прежнюю версию статьи и вектора. |
| Конкурентное редактирование | Вернуть конфликт; повторить операцию с актуальной версией. |
| Старая статья без embedding | Выполнить внешнее первоначальное заполнение с условной записью. |

Пакетное первоначальное заполнение может иметь ограниченные повторы ошибок
провайдера. Это отдельная операция; обычное создание и редактирование
сохраняют новый текст и embedding вместе до успешного завершения запроса.

## 5. Проверка поиска до подключения генерации

Собрать набор вопросов с ожидаемыми источниками: прямые формулировки,
перефразирования, сокращения, точные названия и вопросы без ответа в базе.
Проверять цепочку «вопрос → embedding → RPC → фрагменты» отдельно от LLM.

Измерять попадание нужного источника в первые K результатов, лишние совпадения
и задержку поиска. Настроить разбиение, K и порог сходства по этим измерениям.

Если требуется лучше искать точные термины, отдельной миграцией добавить
tsvector, GIN-индекс и объединение полнотекстовой и векторной выдачи через RRF.
Конфигурация полнотекстового поиска должна подходить языку материалов.

В пилоте scripts/verify-knowledge.mjs проверил шесть русских вопросов:
цены, график, переговорная, Wi-Fi, парковка и отмена. Все ожидаемые источники
найдены; вопросы о погоде и собаках дали fallback. Это небольшой smoke-набор,
а не измерение качества на представительном корпусе.

## 6. Генерация ответа на основе найденных знаний

Реализован answerKnowledgeQuestionUseCase.execute с прямыми импортами:
адаптер embeddings, репозиторий поиска и Groq-клиент; DI отсутствует.

```text
проверка вопроса → embedding → поиск → проверка результатов
→ сборка ограниченного контекста → LLM → проверка ответа и источников
```

Системная инструкция требует опираться на переданные фрагменты, воспринимать
текст статей как данные, отвечать на языке пользователя и сообщать о недостатке
информации. Для пустой или недостаточной выдачи принято поведение:
«Мы обрабатываем ваш запрос». При сбое провайдера сообщать о временной недоступности.

Идентификаторы источников из ответа LLM сверять с реально переданными
фрагментами. Названия и ссылки формировать приложением. Ограничить размер
контекста и ответа; учитывать формат и длину сообщений Telegram.

Первая версия обрабатывает вопрос самостоятельно. Память диалога и разрешение
уточнений вроде «а сколько это стоит?» — отдельное расширение после проверки
основного сценария.

Результат этапа: вопрос преобразуется в ответ с подтверждаемыми источниками
или в предусмотренное сообщение об отсутствии информации.

## 7. Подключение Telegram и защита от повторов

**Реализовано в пилоте:** синхронная обработка запроса после проверки секрета,
sохранение входящего сообщения, claim_telegram_reply с lease на две минуты,
RAG, отправка Telegram и complete_telegram_reply. sent пропускается, busy
возвращает retryable ошибку; fail освобождает попытку после ошибки отправки.
SQL-тест lease прошёл с ROLLBACK. Telegram-адаптер проверяет HTTP и JSON ok,
возвращает фактическую дату отправки. Подтверждённый ответ записывается один раз.

**Следующее расширение — очередь.** Ниже её целевой поток, ещё не реализованный.


Webhook проверяет секрет Telegram, валидирует update, атомарно сохраняет
входящее сообщение и ставит задачу ответа. HTTP 200 возвращается после
успешного сохранения задачи. При ошибке этой операции успешное подтверждение
не отправляется.

Текущий save_telegram_message возвращает void. Новый контракт приёма должен
возвращать признак нового/повторного update, ID входящего сообщения и ID задачи.
Повторный update_id не создаёт вторую задачу.

В задаче сохранять chat_id: он не всегда совпадает с from.id. Worker выполняет
RAG-сценарий и вызывает Telegram API. Адаптер Telegram изменить с возврата void
на возврат message_id и даты отправки с проверкой JSON-ответа API.

После успешной отправки сохранить исходящее сообщение и итоговый статус.
Очередь ответов отделить от индексации, установить таймауты, окно видимости,
предел повторов и состояние исчерпанных попыток. Подтверждать обработку задачи
после сохранения результата; предусмотреть восстановление зависших задач.

Отдельно определить политику неоднозначной отправки: Telegram мог принять
сообщение, а worker — потерять подтверждение или завершиться до записи в БД.
Очередь и дедупликация update не гарантируют абсолютное отсутствие дублей
этого внешнего побочного эффекта.

Результат этапа: бот отвечает через RAG, обычные повторные доставки update
не запускают ответ заново.

## 8. Панель и наблюдаемость

В articles показывать состояние сохранения, ошибку embedding-провайдера или
конфликт редактирования. Успех показывать после записи текста и вектора.
Для старых статей без embedding предусмотреть действие первоначального заполнения.

Для ответа сохранять update_id, найденные статьи и идентификатор embedding-модели, модели, длительность
этапов, расход токенов и итоговый статус. Полные тексты сообщений и секреты
не дублировать в технических логах.

Ограничить длину вопроса, объём контекста, число одновременных задач, частоту
запросов пользователя и бюджет повторных вызовов провайдера.

Результат этапа: состояние знаний и причины ошибок видны оператору.

## 9. Проверки и развёртывание

Проверить SQL-поиск и права, изменение/удаление статей во время генерации embedding,
повторные update, ошибки AI-провайдера и отправки Telegram. Для поиска отдельно
сравнить HNSW с точной выдачей на тестовых вопросах.

Оценить правильность источников, соответствие ответа источникам, поведение
при отсутствии информации, задержку и стоимость. Численные критерии качества
согласовать по результатам пилота; исходных требований к нагрузке и задержке нет.

Порядок публикации: миграции → индексатор → заполнение базы → проверка поиска
→ worker ответов → webhook → обновлённая панель. Первое включение — для
выбранного тестового чата, затем для остальных пользователей.

Учитывать ADR о работе с управляемым Supabase-проектом: полный локальный стек
не запускать без отдельного решения. Применение миграций и публикация функций
должны выполняться в явно выбранном проекте.
